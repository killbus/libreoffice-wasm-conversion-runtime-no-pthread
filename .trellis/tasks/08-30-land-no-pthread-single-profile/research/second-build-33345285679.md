## Runtime failure

The workflow's fresh `tests/converter-gate.test.ts` failed because
`libreofficekit_hook` threw a WebAssembly exception. Running the downloaded
artifact directly with the package loader reproduced the failure and decoded
the Emscripten C++ exception as:

```text
std::runtime_error: osl::Thread::create failed
```

Immediately before the exception LibreOffice reported:

```text
sal/osl/unx/thread.cxx:300: pthread_create failed: EAGAIN
```

The wrapper's `String(error)` conversion hid this detail in CI as
`[object WebAssembly.Exception]`; the direct diagnostic used the generated
module's `getExceptionMessage` runtime method.

## Root cause

Disassembly of stack frame `wasm-function[122246]` matches
`configmgr::Components::writeModifications()` exactly: it checks the
modification target and existing writer at the corresponding object offsets,
allocates the 48-byte `WriteThread`, constructs it, stores it in
`writeThread_`, and calls `salhelper::Thread::launch()` at frame
`wasm-function[24587]`.

The no-pthread profile had already made the LibreOfficeKit main loop and
`comphelper::ThreadPool` synchronous, while upstream already disables SAX
parser and ZIP read-ahead threads under Emscripten. It had not adapted the
configuration writer, which is entered during startup when LOK commits locale
and other settings.

## Correction

For `__EMSCRIPTEN__`, `Components::writeModifications()` now calls
`writeModFile()` synchronously while the caller owns the configuration lock.
The non-Emscripten delayed writer remains unchanged. Its existing non-fatal
handling of configuration persistence errors is preserved. In addition,
`salhelper::Thread::launch()` includes the thread name in creation failures so
any remaining unsupported thread path is immediately identifiable.
